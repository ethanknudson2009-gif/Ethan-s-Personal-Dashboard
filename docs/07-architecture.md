## 3. Time & timezone (America/Phoenix)

Arizona (except the Navajo Nation) does **not** use daylight saving time. Phoenix is **UTC−7 all year**. Vercel servers run in UTC, and other states' clocks shift twice a year, so time handling follows strict rules:

1. **The database stores instants as `timestamptz` (UTC).** Calendar-only facts (a holiday, a food log's day) are stored as `date`.
2. **Every user has a `timezone` setting** (default `America/Phoenix`). All "what day is it?" logic uses `lib/time` helpers that take this zone. Code never calls `getDay()`, `getHours()` or `toLocaleDateString()` without a zone, and never hard-codes "−7". If Ethan moves to another state, changing the setting just works.
3. **Local wall time → UTC** goes through `@date-fns/tz` (`TZDate`). Example: "Fri 11:59pm" typed on Tue Nov 10, 2026 becomes Fri Nov 13 23:59 Phoenix time, stored as `2026-11-14T06:59:00Z`.
4. **Tests pin the behavior**, including DST weekends elsewhere (e.g. Mar 8 and Nov 1, 2026): Phoenix times must not move by an hour on those dates.
5. **"Due at midnight"** is stored as 23:59 that day, because students mean the end of that day, not the start.

## 4. Data model

All tables live in Postgres (Supabase). Conventions for **every user-owned table**:

- `id uuid primary key default gen_random_uuid()`
- `user_id uuid not null default auth.uid() references auth.users on delete cascade`
- `created_at timestamptz default now()`, `updated_at timestamptz` (kept current by a trigger)
- `deleted_at timestamptz null` → **soft delete** for the 7-day Trash (§8)
- `source text` where useful: `manual | quick_add | shortcut | mcp | syllabus`

Tables are **created in the phase that needs them** (Phase 1 migration = profiles, schedule, classes, tasks, events, time blocks, inbox, tokens). They are all designed now so they fit together.

## 5. Row Level Security (RLS) & room for social

RLS is switched **on for every table**. For user-owned tables, one pattern repeats:

```sql
alter table tasks enable row level security;
create policy "own rows" on tasks
  for all
  using (user_id = auth.uid())
  with check (user_id = auth.uid());
```

- Child tables (`workout_sets`, `class_meetings`…) also carry `user_id`, so the same one-line policy works without joins.
- Shared reference data (`exercises` with `user_id is null`) gets an extra read-only policy: `for select using (user_id is null)`.
- Storage bucket `user-files` is **private**. Its policy only allows paths that start with your own user id: `{user_id}/{file_id}.pdf`.
- **Server-only "admin" access.** `/api/capture`, `/api/mcp` and `/api/cron` are called by Shortcuts, Claude or pg_cron, not by a logged-in browser. After checking a private token, they use the Supabase *secret* key, which bypasses RLS. To stay safe, that key is only used inside `lib/supabase/admin.ts`, through helper functions that **always** take the `userId` found from the token and add `user_id = userId` to every query. Tests cover this.
- **Signups:** after Ethan creates his account, "Allow new users to sign up" is turned off in Supabase until Phase 5, so strangers can't make accounts.

**Room for Phase 5 (social), no tables yet:**
- `profiles` stays private. Phase 5 adds a separate `public_profiles` (username, avatar, opt-in flags) so private settings never leak.
- `friendships` (requester, addressee, status), `groups`, `group_members` (role), `challenges`, `challenge_entries`.
- Leaderboards read **only totals** (from `xp_events`, habit streaks, workout counts) through Postgres functions that check "is this person my friend / in my group, and did they opt in?". Friends never get direct access to anyone's tasks, food or money tables.
- Because every row already has `user_id`, none of the existing tables need to change for social features.

## 6. Capture API: `POST /api/capture`

Used by the iPhone "Log It" Shortcut. It is a private address protected by a per-user token.

**Request**
```
POST https://<our-app>.vercel.app/api/capture
Authorization: Bearer <capture token from Settings → Tokens>
Content-Type: application/json
```

**JSON body (version 1).** Only `raw_text` is required. Everything else is optional.

```jsonc
{
  "v": 1,
  "raw_text": "bio lab report due friday 11:59pm, about 2 hours",   // always send the original words
  "type": "homework",          // homework | task | food | workout | expense | job | note | habit
  "title": "Bio lab report",
  "due_text": "Fri 11:59pm",   // the date words exactly as said; OUR parser turns this into a date
  "due": "2026-11-13T23:59",   // optional ISO local time (no offset) or "2026-11-13"; checked against due_text
  "class_name": "bio",
  "estimate_minutes": 120,
  "amount": 12.00,             // dollars: expense, or job income
  "category": "gas",           // expense category
  "food": [{ "name": "egg", "quantity": "2", "calories": 140, "protein_g": 12, "carbs_g": 1, "fat_g": 10 }],
  "exercises": [{ "name": "bench press", "sets": [{ "reps": 10, "weight_lb": 135 }], "duration_minutes": null, "distance_mi": null }],
  "habit_name": "read",
  "customer_name": "Mrs. Lopez",
  "job_date_text": "Saturday 9am",
  "notes": "",
  "confidence": 0.9,           // Claude's own guess, 0–1
  "client_id": "8f1c…"         // optional: unique id so a retried send isn't saved twice
}
```

Why both `due_text` and `due`: **language models sometimes get dates wrong**, and our parser is exact and tested. The server parses `due_text` itself. If Claude's `due` disagrees, the item gets a problem note and confidence is lowered.

**What the server does**
1. It hashes the token and finds the user (`api_tokens`, scope `capture`, not revoked). A bad token returns `401`.
2. It validates the body with zod. Unknown fields are ignored. An oversize body (>32 KB) returns `413`.
3. **Only `raw_text` arrived** (the fallback when Claude is unavailable)? It runs our parser (§7) to build the draft.
4. **Claude's JSON arrived?** It still runs our parser over `due_text`, `class_name`, `job_date_text` and amounts, then merges the two.
5. It decides where the item goes (§8): saved directly, or into the Inbox.
6. It replies with a short message for the Shortcut to show:

```json
{ "ok": true, "status": "inbox", "id": "…", "message": "📥 To review: Bio lab report · Biology · due Fri 11:59 PM" }
{ "ok": true, "status": "saved", "id": "…", "message": "Saved ✓ $12.00 · Gas" }
```

**Ask Claude instructions inside the Shortcut** (we write them ourselves; the exact text goes in the setup guide in Phase 2): *"Turn what I said into one JSON object with these fields… Copy any date or time words exactly into due_text instead of working out the date. Output only JSON."*

`POST /api/capture/file` (Phase 2) accepts `multipart/form-data` with one file (PDF/image, ≤ 10 MB) plus an optional `class_name`. It stores the file and replies "Saved ✓ syllabus.pdf · ask Claude to import it".

## 7. Our own natural-language parser (no paid AI)

`lib/parser` is a pure function:

```ts
parse(text: string, ctx: { now: Date; timeZone: string; classes: ClassRef[]; habits: string[] }): CaptureDraft
// CaptureDraft = same shape as the capture JSON + confidence + problems[]
```

**Steps, in order**
1. **Normalize:** lowercase a copy, tidy spaces, expand shorthands (`tmrw`→tomorrow, `hw`→homework, `w/`→with). The original text is kept for the title.
2. **Money:** `$12`, `12 dollars`, `$12.50`. Becomes `amount` and is removed from the title.
3. **Date words:** `today`, `tonight`, `tomorrow`, weekday names and short forms (`fri`, `thurs`), `this/next <weekday>`, `in 3 days`, `in 2 weeks`, `11/13`, `nov 13`, `the 13th`, `end of week` (Friday), `weekend` (Saturday).
4. **Time words:** `11:59pm`, `11:59 pm`, `3pm`, `15:00`, `noon`, `midnight` (→ 23:59), `at 3`, `by 5`. A bare hour with no am/pm: **1–7 means PM, 8–11 means AM** (homework is rarely due at 3 AM). The test suite covers this rule.
5. **Resolving weekdays:** "Fri" means the next Friday from today. If today is Friday, it means today when the time is still ahead (or no time was given), otherwise next week.
6. **Type keywords** (first match wins, ordered most specific first):
   - expense: `spent`, `paid`, `bought`, `$`
   - food: `ate`, `had`, `drank`, `breakfast`, `lunch`, `dinner`, `snack`, `calories`
   - workout: `bench`, `squat`, `ran`, `run`, `miles`, `sets`, `reps`, `3x10`, `gym`, `lifted`
   - job: `job`, `washed`, `windows`, `customer`, `quote`
   - habit: matches one of your habit names, or `did my …`
   - note: starts with `note`, `journal`, `remember that`
   - homework: `due`, `homework`, `essay`, `lab`, `quiz`, `test`, `exam`, `project`, `worksheet`, or a class name
   - otherwise: task
7. **Class match:** compare words against each class's `name` + `short_names` ("bio" → Biology). Exact word first, then a "starts with" match.
8. **Amounts in other types:** `2 eggs` → food quantity 2; `3x10 @135` or `3 sets of 10 at 135` → sets/reps/weight; `about 2 hours` / `45 min` → `estimate_minutes`.
9. **Title:** the original text minus the recognized date/time/money parts and filler words (`due`, `by`, `on`, `at`), trimmed and capitalized.
10. **Confidence:** start at 1.0 and subtract for each doubt: type guessed by default (−0.4), class word not matched (−0.2), homework without a due date (−0.3), bare hour that needed the AM/PM rule (−0.1), food without calories (−0.3, our parser doesn't know calories). Each doubt also adds a readable `problems` entry.

**Examples (become tests)**, with "now" = Tue Nov 10, 2026, 4:00 PM Phoenix:

| Input | Result |
|---|---|
| `bio lab due Fri 11:59pm` | homework · "Lab" · Biology · due 2026-11-13 23:59 MST (= 2026-11-14 06:59Z) |
| `ate 2 eggs` | food · "Eggs" · quantity 2 · calories missing → Inbox |
| `spent $12 gas` | expense · $12.00 · category "gas" |
| `math worksheet tomorrow` | homework · Math (if that class exists) · due 2026-11-11, no time (shown as "end of day") |
| `wash Lopez windows sat 9` | job · Sat Nov 14 09:00 · customer "Lopez" |

## 8. Review-before-save, Inbox and 7-day Trash

**Where a capture goes**

| Came from | Goes to |
|---|---|
| Quick-add box in the web app | A **preview line** under the box ("Homework · Biology · due Fri 11:59 PM"). You press Enter to save or tap a field to fix it. Seeing it first *is* the review. |
| Shortcut, raw text only | **Inbox**, always |
| Shortcut with Claude's JSON | **Inbox** by default (D8). Saved directly only if its type is in `auto_save_types` **and** confidence ≥ 0.85 **and** there are no `problems`. |
| Claude connector (MCP) | **Inbox**, unless Claude says you confirmed it in the chat (§10) |
| Syllabus import | **Inbox batch** with a checklist screen |

**Inbox screen:** each card shows the raw words, the proposed record and any problems in plain language. Buttons: **✓ Approve** (one tap), **Edit** (opens the normal form, already filled in), **Dismiss**. There's also an **Approve all without problems** button at the top. Approving creates the real row and records `result_table`/`result_id`.

**Trash (7 days):** "Delete" sets `deleted_at = now()`. Normal screens hide those rows. The Trash screen lists them with **Restore** (clears `deleted_at`) and the number of days left. A scheduled job (§13) permanently removes rows whose `deleted_at` is older than 7 days. Files in Storage are removed at the same time.

## 9. Logic modules

### 9.1 The Cushion (`lib/cushion`)
"Hours you have minus hours you need," calculated across **all open assignments together**, so two things due Friday share the same evenings.

- **Capacity per day** = `study_minutes[weekday]` from Settings (default 120 Mon–Fri, 0 Sat–Sun). *v1 keeps it simple: it does not subtract calendar events. A later version can subtract events that overlap study time.*
- **Today** counts only the part of today's capacity left before `study_end_time` (22:00): `min(capacity, minutes until 22:00)`.
- **The due day itself** counts only if the due time is 8:00 PM or later (an 11:59 PM deadline leaves the evening to work; an 8 AM deadline doesn't).
- **Remaining work** for a task = `max(estimate_minutes − minutes_done, 0)`. If there's no estimate, the default is 30 minutes and the card shows "estimate?".
- Sort open assignments by `due_at` (earliest first). For each one:
  `cushion_i = capacity(now → due_i) − Σ remaining work of every open assignment due on or before due_i`
- **Label:** cushion ≥ 60 min → 🟢 *ahead*; 0–59 → 🟡 *tight*; < 0 → 🔴 *behind* ("need 1 h 30 m more than you have").
- Pure function: `cushion(tasks, settings, now, timeZone) → Map<taskId, { minutes, label }>`.

### 9.2 Repeats (`lib/repeat`)
`repeat` jsonb:
```jsonc
{ "mode": "fixed" | "after_completion",
  "every": 1, "unit": "day" | "week" | "month",
  "weekdays": [1, 3],        // optional, for "every Mon and Wed" (fixed only)
  "until": "2027-05-28" }    // optional end date
```
- **fixed:** the next due date comes from the *previous due date* ("every Monday").
- **after_completion:** the next due date comes from *when you actually finished* ("water plants 7 days after I last did it", "wash Lopez windows 8 weeks after the last job").
- When a repeating task is marked done, the app creates the next task in the same `series_id`, keeping the due time of day in your time zone. A month repeat on the 31st goes to the last day of shorter months.
- Pure function: `nextDue(rule, previousDue, completedAt, timeZone) → Date | null`.

### 9.3 School schedule rotation (`lib/schedule`)
- **School day** = a weekday listed in `school_weekdays` (Ethan: Mon–Thu), inside the term, not in `no_school_days`, and not overridden as `no_school`.
- **weekly** schedules: classes meet by weekday.
- **rotating** schedules (A/B, block, 6-day cycles): the label for a date = `day_labels[(anchor index + number of school days between anchor_date and date) mod length]`. Only **school days** advance the rotation, so a holiday doesn't "eat" a B day. `schedule_overrides` can force a label.
- Pure function: `dayInfo(date, schedule, noSchoolDays, overrides) → { isSchoolDay, label | null }` and `classesOn(date, …) → meetings[]`. Tests cover counting backward from the anchor, holidays, and term edges.

## 10. MCP server (Claude custom connector)

- **Where:** `src/app/api/mcp/route.ts`, a remote MCP server using the official `@modelcontextprotocol/sdk` with the **Streamable HTTP** transport in **stateless** mode (each request stands alone, which fits Vercel's serverless functions).
- **Auth:** on claude.ai → Settings → Connectors → Add custom connector, Ethan enters the URL `https://<our-app>.vercel.app/api/mcp`, chooses **No sign in**, and under **Request headers** adds `Authorization: Bearer <mcp token>`. The token (scope `mcp`) is created in our Settings → Tokens. It is separate from the Shortcut's token, so either one can be revoked alone. A missing or wrong token returns `401`. The connector then works in Claude on web, desktop and iPhone. *(Optional later: real OAuth sign-in using Supabase as the login server.)*
- **Tools** (each with a zod input schema and a plain-language description Claude reads):

| Tool | Does | Writes? |
|---|---|---|
| `get_today` | Today's classes (with A/B label), Do Now / Up Next / Due Soon, Inbox count | read |
| `list_due` | Open tasks/assignments in a date range, with Cushion labels; filter by class | read |
| `add_task` | A task (title, due text, repeat, priority) | Inbox* |
| `add_assignment` | An assignment (class, title, due text, estimate) | Inbox* |

## 11. Syllabus / PDF upload

1. **Upload** on the Classes page (or the Share Sheet → `/api/capture/file`). The file goes to the private Storage bucket at `user-files/{user_id}/{file_id}.pdf` and gets a `files` row. Free tier: 1 GB total; we cap files at 10 MB.
2. **Text extraction in the browser** with `pdfjs-dist`. It's free and runs on your device, so the server doesn't need to. The text is saved to `files.extracted_text`. Photos and scanned PDFs have no text layer, so they're marked "needs Claude to read."
3. **Claude does the understanding.** In the Claude app, Ethan says *"import my new Biology syllabus."* Claude calls `list_files` → `get_file_text`, pulls out assignments/exams/dates/grade weights/late policy, and calls `import_syllabus`. For a photo or scan, Ethan attaches it directly in the Claude chat and Claude reads it there.
4. **Review screen:** the batch appears in the Inbox as a checklist (✓ each row, edit dates, pick the class). **Approve selected** creates the tasks and grade categories. The file stays attached to its class.

There is no paid API anywhere: the "AI" step is Ethan's own Claude Pro chat using our connector.

## 12. PWA & web push (iPhone 13, iOS 26)

**Install:** `app/manifest.ts` sets `name`, `short_name` ("Dashboard"), `display: "standalone"`, `start_url: "/today"`, theme/background colors and icons (192, 512, maskable). The layout adds `appleWebApp` metadata and a 180×180 `apple-touch-icon`. Ethan opens the site in Safari → Share → **Add to Home Screen**. It opens full screen from its own icon. Login happens once inside the installed app (D1). Home Screen web apps are exempt from Safari's 7-day storage wipe, so the session stays.

**Service worker** (`public/sw.js`, hand-written, small): handles only `push` (show the notification) and `notificationclick` (open the right page, plus action buttons like Done / +1 h / Tomorrow). It does no offline caching (D2).

**Web push (Phase 2):**
- Uses the free Web Push standard with **VAPID keys** we generate ourselves (`npx web-push generate-vapid-keys`). No account or service is needed.
- iPhone only allows push **after Add to Home Screen** and only when you tap a button. So Settings has an **"Turn on notifications"** button, and the app shows instructions if it's opened in plain Safari.
- The subscription is saved to `push_subscriptions`. `/api/cron/tick` (§13) decides what to send: the morning digest (7:00 AM), tomorrow's preview (8:00 PM), due-soon reminders timed by the Cushion, and repeat nags based on each item's `nag_level`. Quiet hours: 22:00–7:00.

## 13. Scheduled jobs

Supabase Free includes the **`pg_cron`** and **`pg_net`** extensions, so no new service is needed:
- **Every 15 minutes:** `pg_cron` calls `POST /api/cron/tick` with `Authorization: Bearer <CRON_SECRET>`. That route sends any due notifications (Phase 2). These regular calls also keep the free Supabase project from pausing after a week of no use.
- **Daily at 3:00 AM Phoenix (10:00 UTC):** a SQL job permanently deletes Trash rows older than 7 days (Storage files are removed by the tick route).
